# R2T2 重构验收记录

日期：2026-09-25。服务已运行于 `0.0.0.0:4174`，首页进入录音页面。容器 `qwen3-asr-realtime-asr-1`，镜像 `local/qwen3-asr:r2t2`。实时引擎为 vLLM AsyncLLM；离线仍为项目已有的 Qwen3-ASR-1.7B，保留词级对齐和离线说话人处理。

## 环境与样本

- GPU：RTX PRO 6000 96 GB，宿主机 GPU 1；实时引擎启用 CUDA graph，接入上限 4。
- 模型和算法版本见 [实时部署文档](../realtime.md#解码与版本)。
- 中文：NetEase R2T2 上游 `resources/test.wav`，6.74 秒；本地验收副本 `tests/files/realtime/zh.wav`。
- 英文：Qwen 官方示例 `asr_en.wav` 前 7 秒，末尾截断在说话过程中；本地验收副本 `tests/files/realtime/en.wav`。
- 客户端按真实时间每 160 ms 发送一帧，经公共 API 转发到实时引擎。
- 原始结果：项目本地 `benchmark_results/r2t2-acceptance.json`，由 `scripts/benchmark/realtime_smoke.py` 生成。

## 实测

| 场景 | 首字时间 | 帧处理延迟 P95 | 结束补齐延迟 |
| --- | ---: | ---: | ---: |
| 单路中文 | 1792 ms | 44 ms | 16 ms |
| 单路英文 | 1793 ms | 35 ms | 32 ms |
| 四路同时输入（两中两英） | 1807–1810 ms | 53–67 ms | 40–45 ms |
| 41.22 秒中英文重复录音 | 1792 ms | 44 ms | 43 ms |

首字从音频发送时间轴起点计算，包含音频本身的上下文等待；帧处理延迟是收到事件时间减去事件对应音频时间，不能当作说话到文字出现的延迟。以上是该机器、这些样本及四路负载下的一次验收，不代表最大容量或所有语料的延迟上界。

四路会话各自输出对应音频，没有发现其他会话的文字串入。三路逐字匹配单路基线；一路英文末尾的 `and` 变成 `in`，归一化字符编辑距离 3.33%。因此保留逐路原始文本，不宣称并发输出必然逐字一致。

中→英与英→中之间加入 0.5 秒静音，两种顺序都输出了两种语言。41.22 秒样本直接重复拼接中英文三次，完整输出三轮内容，共 88 次非空文字增量。此音频自身存在停顿，不能据此宣称任意无停顿语言切换已经解决；持续背景噪声也可能阻止低能量边界触发。

## 其他验证

- 42 项 unittest 通过，覆盖协议校验、连接容量、独立会话状态、断线释放、取消请求、队列上限、滚动窗口、英文空格、`language None` 元数据及停顿后重置语言前缀。
- 四个连接占满时，第五个连接明确收到 `capacity_exceeded`；连接关闭后可以立即重新接入，无残留名额。
- Chromium 假麦克风注入真实 WAV，桌面 1280×800 和手机尺寸 390×844 均完成开始、停止、末尾补齐、再次录音；无页面异常或横向溢出。此项是桌面浏览器的移动尺寸模拟，不是实机手机兼容性认证。
- 离线 `/v1/audio/transcriptions` 对同一中文音频正常返回文本及词级时间戳。
- 新代码 Ruff 检查与 `git diff --check` 通过。

本次没有运行 910B 测试。现有 CUDA 镜像及启动器不能直接用于 NPU；旧版 [昇腾研究](ascend-910b-feasibility.md) 已标注实时架构过期。
